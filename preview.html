Trust, by construction

Every shop gets its own locked room.

Multi-tenancy is not a dropdown in the UI. It is a database boundary. The request resolves a workspace, the workspace sets the transaction context, and PostgreSQL row-level security decides what exists.

  • RLS is fail-closed: no tenant context means zero rows, not every row.
  • Plan gates are checked in the API, not just hidden in the interface.
  • Public estimates, reviews and status pages use random, scoped tokens.
  • Security headers, role checks and audit entries are part of the request path.

01 The locked room: workspaces and RLSWhy one database can serve many shops safely

A workspace (or tenant) is one shop’s account. Every customer, vehicle, order and invoice belongs to exactly one workspace.

  • Tenant context is resolved from the request: a header, a subdomain or a verified custom domain.
  • Row-level security is a PostgreSQL policy that filters rows by that context — even if application code forgets a filter.
  • Fail-closed means no context produces no rows. It never means “show everything.”
02 The job lifecycleFrom booking request to closed invoice

A booking is an inbound request. A service order is the operational job the shop owns, with a status and a timeline.

  • Statuses move from scheduled through in progress and awaiting parts to completed, invoiced or cancelled.
  • Line items separate labour from parts, which keeps totals and exports honest.
  • The status link is public but tokenized: the customer sees one job, not the workspace.
03 Evidence, not adjectivesHow a photo inspection changes the conversation

A DVI is a checklist with condition, notes and photos. It turns “your brakes are worn” into “3 mm remaining, here is the photo.”

  • Items can be marked for attention and included in the estimate conversation.
  • Completed inspections lock, so the evidence cannot be rewritten later.
  • Customers see the relevant photo on the status page without a login.
04 The money pathEstimate, approval, invoice, payment

An estimate proposes work. An invoice requests payment. Keeping them separate protects the shop and the customer.

  • An estimate token lets the customer approve or decline without an account.
  • Invoices track draft, sent, paid, overdue and void; revenue on the dashboard means paid, not promised.
  • Stripe checkout collects the card payment; accounting adapters and CSV export carry the journal.
05 The retention loopReviews, reminders and the outbox

The cheapest customer is the one already in your database. The loop closes the day with a review ask and brings the next service forward with a reminder.

  • Segments select customers by real criteria, not a copied spreadsheet.
  • Campaigns preview the message and count recipients before sending.
  • The outbox records sent, skipped and failed. “Skipped” is honest when SMS is not configured.
06 Operating safelyRoles, entitlements, audit and tokens

A feature is not secure because the button is hidden. It is secure when the API refuses the request anyway.

  • Roles decide who can change money, people and settings; viewers read.
  • Entitlements decide which plan features the workspace may use, on the server.
  • Audit entries, scoped tokens and security headers make the boundary observable.

Straight answers

Questions, answered plainly.

If something here sounds too good, it probably needs a provider key, a migration or a real-world test. That is the honest version.

Can I try it without Stripe or an email provider?

Yes. The seeded demo runs with a safe stub billing provider. Email and SMS messages are recorded in the outbox as Skipped when credentials are absent, so the workflow stays truthful without pretending a message left the building.

Is one shop’s data really invisible to another?

The API runs as a non-owner database role with row-level security enabled. Every tenant-owned query runs inside a transaction with the resolved workspace context. A missing context is fail-closed: zero rows, not every row.

Does it send real email or text messages?

It can, through SMTP and a Twilio-compatible SMS adapter. Without credentials, delivery is marked skipped. Real deliverability, sender reputation and opt-in compliance still need provider-side testing.

Can I put my own brand and domain on it?

On Pro and Enterprise, yes: logo, colours, support email and a custom domain. Domains are verified with a TXT record before the edge will route them, and certificates are issued on demand.

Is this a finished commercial SaaS?

It is a production-shaped foundation. Billing defaults to a stub, certifications and penetration testing are not included, supplier and accounting adapters need credentials, and there is no cross-region failover. Add a license and complete a security review before selling it as a service.

What is it built with?

A Next.js 16 App Router frontend, a FastAPI/Python API, PostgreSQL with row-level security, Redis for throttling, and Caddy at the edge. Docker Compose runs the whole stack locally; the frontend is installable as a PWA.
